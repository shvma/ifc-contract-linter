# ifc-contract-linter — когда мягкий контракт инструмента пропускает утечку

Детерминированный монитор потока данных для AI-агентов (на примере [OpenAPPA](https://github.com/archestra-ai/openappa)) разрешает или запрещает каждый вызов инструмента по его **контракту** — декларации о том, что инструмент делает с данными. Монитор исполняет контракт буквально. Если контракт описывает эффект инструмента мягче, чем он есть на самом деле, утечка проходит, а монитор её не видит: сам он работает верно — неполна картина мира.

Этот репозиторий показывает такой зазор на реальном поставляемом контракте и даёт инструмент, который его ловит:

- **Находка.** В поставляемом контракте Google Drive (OpenAPPA, v0.34.0–v0.37.0) запись, копирование и перенос файла проходят без ревью, которого требует явная выдача доступа (`share_file`). При этом Google Drive отдаёт файлу права папки-получателя. Положить доверенный внутренний файл в папку с внешним доступом — это шаринг наружу мимо ревью.
- **Линтер** (`checker/`) — проверяет контракт как код: находит операции, которые расширяют круг читателей, но не требуют ревью.
- **Воспроизведение** (`replay/`) — детерминированные трассы `appa replay` на **дословных** правилах контракта: показывают решение монитора (`allow`/`deny`) без модели, сети и реального Drive.

Сообщено в проект: [archestra-ai/OpenAPPA#747](https://github.com/archestra-ai/OpenAPPA/issues/747).

## Находка подробно

Контракт Google Drive защищает **явную** выдачу доступа: у `share_file` стоит метка ручного ревью. Но у доступа в Drive есть второй путь — наследование от папки. Из справки Google:

> «When you share a folder, all files and subfolders inside it inherit those same sharing permissions.»

Операции записи — `create_file`, `copy_file`, `update_file` — требуют лишь `trust = "trusted"` и аудиторию, содержащую `internal`; ручного ревью у них нет, аргумент папки-получателя контракт не смотрит. Перенос отдельного инструмента не имеет — он спрятан в `update_file` с аргументом `parentId` («resulting in a folder move»). Поэтому доверенные внутренние данные можно записать, скопировать или перенести в папку с внешним доступом, и монитор это пропустит.

Аналогия из сетевой безопасности: межсетевой экран режет исходящий трафик на 443, но пропускает DNS — правило выполнено дословно, а данные ушли туннелем, о котором правило не знает.

## Что это не

Путь «инъекция в документе Drive → агент кладёт файл в открытую папку» контрактом **закрыт**: любое чтение из Drive метит траекторию `suspicious`/`self`, а запись требует `trusted`/`internal` (это видно в `results/deny-reasons.txt`, и авторы контракта закладывали это сами). Значит, внешний атакующий через инъекцию сюда не проходит. Остаются ошибка модели («сохрани в эту папку», а папка открыта по ссылке), ошибка пользователя и инсайдер, заранее открывший папку наружу. Риск ниже, чем «внешняя утечка».

Воспроизведение доказывает ровно одно: на этих траекториях монитор говорит `allow`. Что файл в открытой папке действительно виден снаружи — это документированное поведение Google Drive (наследование доступа папкой), а не результат стенда. Оговорки развёртывания (например, запрет внешнего доступа администратором Workspace) не проверялись.

## Как воспроизвести

```bash
./run.sh
```

Нужны Python 3.11+ (или пакет `tomli`) и бинарь `appa` 0.34.0 (`appa-aarch64-apple-darwin`, релиз GitHub OpenAPPA; кладётся в `~/.local/bin/appa`). Если `appa` не установлен, линтер всё равно отрабатывает, а секция replay пропускается.

Что печатает `run.sh`:

1. проверку sha256 закреплённого снимка контракта;
2. тесты линтера;
3. линтер на поставляемом контракте — **3 пробела** (`create_file`, `copy_file`, `update_file` без ревью);
4. линтер на черновике исправления — пробелов нет;
5. `appa replay` на дословных правилах поставляемого контракта (**gap**) и на черновике исправления (**fixed**), плюс пробы формата;
6. причину каждого отказа (`results/deny-reasons.txt`).

## Результаты

| Проверка | Итог |
|---|---|
| Тесты линтера | 15/15 |
| Линтер на поставляемом контракте | 3 пробела (`create_file`, `copy_file`, `update_file`) |
| `appa replay`, правила поставляемого контракта (gap) | 6/6 трасс: запись, копия, перенос в общую папку — `allow`; инъекция через Drive — `deny` |
| `appa replay`, черновик исправления (fixed) | 11/11 трасс: перенос в общую папку — `deny` (ревью); внутренние папки — `allow`; один **остаточный зазор** — `allow` (документирован, см. ниже) |
| Пробы формата политики | 3/3 |

Сырьё — в `results/` (пересчитывается `./run.sh`): решения монитора (`appa-replay.txt`), причины отказов (`deny-reasons.txt`), прогон линтера (`linter-run.txt`), снимок контракта и сверка версий.

## Структура

```
checker/     линтер контракта (contract-as-code) + тесты + inventory.json
replay/      модели контракта и .appa-трассы для appa replay; разбор в replay/README.md
results/     сырые результаты прогонов, снимки контракта
WRITEUP.md   технический разбор: как устроен монитор и почему зазор срабатывает
SOURCES.md   источники с цитатами и закреплёнными версиями
run.sh       воспроизведение одной командой
```

## Исправление

Черновик исправления (`replay/fixed/`) выражает меру средствами самого формата контракта: запись в папку из белого списка внутренних папок идёт без ревью, любая другая запись — с ревью (fail-closed). Это закрывает три пути переноса данных в открытую папку (`create_file`, `copy_file`, `update_file`).

У меры есть **остаточный зазор**, не закрываемый в этом формате: селектор сравнивает только строковые аргументы, поэтому правило `update_file(parentId:<внутренняя папка>)` без ревью совпадает первым и пропускает заодно булевы флаги доступа. В итоге смена доступа — `writersCanShare: true`, `inheritedPermissionsDisabled: true` — при переносе в папку из белого списка проходит **без ревью** (трасса `replay/fixed/residual-writerscanshare-via-allowlist.appa`, подтверждено `appa`). Так ограничение языка политики режет в обе стороны: оно и гасит инструмент целиком там, где хватило бы точечного правила, и пропускает опасный булев флаг там, где вызов совпал с разрешающим правилом по строке.

Полностью зазор закрывает только вариант (в) — перед записью спросить Drive о фактическом доступе цели; это код в источнике аудитории, а не правка контракта. Варианты меры и их цена разобраны в `WRITEUP.md` и в issue #747.
