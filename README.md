# ifc-contract-linter — когда мягкий контракт инструмента пропускает утечку

**Тяжесть:** design limit контракта, не уязвимость движка; low–medium.

Детерминированный монитор потока данных для AI-агентов (на примере [OpenAPPA](https://github.com/archestra-ai/openappa)) разрешает или запрещает каждый вызов инструмента по его **контракту** — декларации о том, что инструмент делает с данными. Монитор исполняет контракт буквально. Если контракт описывает эффект инструмента мягче, чем он есть на самом деле, утечка проходит, а монитор её не видит: сам он работает верно — неполна картина мира.

Этот репозиторий показывает такой зазор на реальном поставляемом контракте и даёт инструмент, который его ловит:

- **Находка.** В поставляемом контракте Google Drive (OpenAPPA, v0.34.0–v0.37.0 и `main` на 2026-10-30) запись, копирование и перенос файла проходят без ревью, которого требует явная выдача доступа (`share_file`). При этом Google Drive отдаёт файлу права папки-получателя. Положить доверенный внутренний файл в папку с внешним доступом — это шаринг наружу мимо ревью.
- **Линтер** (`checker/`) — проверяет контракт как код: находит операции, которые расширяют круг читателей, но не имеют меры (ревью, аудитории цели из аргумента, `forwards`).
- **Воспроизведение** (`replay/`) — детерминированные трассы `appa replay` на **дословных** правилах контракта: показывают решение монитора (`allow`/`deny`) без модели, сети и реального Drive. Три модели: поставляемый контракт, черновик исправления и контракт из PR мейнтейнера.

| Сценарий | PR #750 | Почему |
|---|---|---|
| запись, копия, перенос в папку, открытую по ссылке (пример issue) | **deny** | аннотатор спрашивает права цели и требует `public` |

| `writersCanShare: true` | **allow** — остаток | аннотатор смотрит только `fileId` и `parentId` |
| `inheritedPermissionsDisabled: false` без переноса | **allow** — остаток | папка снова наследует права родителя, а родителя аннотатор не спрашивает |
| снять `downloadRestriction` без переноса | **allow** — остаток | круг читателей не меняется; метки аудитории меру DLP не выражают |
| `parentId`, которого Drive не знает | отказ без решения политики | 404 роняет аннотатор, монитор отказывает (fail-closed) |

Первые два остатка ученик сообщил в публичном комментарии к PR #750 2026-10-29; трассы это подтверждают. Replay шёл на движке `appa` 0.34.0, а PR целит в `main`: на движке из `main` не прогонялось.

## Находка подробно

Контракт Google Drive защищает **явную** выдачу доступа: у `share_file` стоит метка ручного ревью. Но у доступа в Drive есть второй путь — наследование от папки. Из справки Google:

> «When you share a folder, all files and subfolders inside it inherit those same sharing permissions.»

Операции записи — `create_file`, `copy_file`, `update_file` — требуют лишь `trust = "trusted"` и аудиторию, содержащую `internal`; ручного ревью у них нет, аргумент папки-получателя контракт не смотрит. Перенос отдельного инструмента не имеет — он спрятан в `update_file` с аргументом `parentId` («resulting in a folder move»). Поэтому доверенные внутренние данные можно записать, скопировать или перенести в папку с внешним доступом, и монитор это пропустит.

У `update_file` есть и аргументы, которые меняют доступ без переноса. Опасен `inheritedPermissionsDisabled: false`: схема коннектора — «false to re-enable inherited permissions», папка снова получает читателей родителя. `true`, наоборот, сужает круг читателей («restricting access to only users with direct permissions on the folder», `results/connector-tools-list-2026-10-29.json`). Рядом `writersCanShare: true` (любой редактор может расшарить файл) и `downloadRestriction` (запрет скачивать и копировать).

Аналогия из сетевой безопасности: межсетевой экран режет исходящий трафик на 443, но пропускает DNS — правило выполнено дословно, а данные ушли туннелем, о котором правило не знает.

## Что это не

Путь «инъекция в документе Drive → агент кладёт файл в открытую папку» контрактом **закрыт**: любое чтение из Drive метит траекторию `suspicious`/`self`, а запись требует `trusted`/`internal` (это видно в `results/deny-reasons.txt`, и авторы контракта закладывали это сами). Значит, внешний атакующий через инъекцию сюда не проходит. Остаются ошибка модели («сохрани в эту папку», а папка открыта по ссылке), ошибка пользователя и инсайдер, заранее открывший папку наружу. Отсюда и тяжесть: не уязвимость движка, а предел контракта, который нужен для утечки без участия внешнего атакующего.

Воспроизведение доказывает ровно одно: на этих траекториях монитор говорит `allow`. Что файл в открытой папке действительно виден снаружи — это документированное поведение Google Drive (наследование доступа папкой), а не результат стенда. Оговорки развёртывания (например, запрет внешнего доступа администратором Workspace) не проверялись.

## Как воспроизвести

```bash
./run.sh
```

Нужно:

- Python 3.11+ (или Python 3.9+ с пакетом `tomli`) — линтер и тесты;
- `appa` 0.34.0 — replay. Ищется в `$APPA`, в `PATH`, затем в `~/.local/bin/appa`;
- Python 3.10+ — модель PR #750: `drive-readers.py` из PR использует `match`. `run.sh` ищет `python3.13`…`python3.10`, `python3` и Python, поставленный `uv`; путь можно задать в `PY310`.

Без `appa` или без Python 3.10+ `run.sh` прогоняет тесты и линтер, а потом выходит с кодом **2**: replay не запускался, проверка неполная. Код 0 — только когда совпало всё, включая replay.

Установка `appa` 0.34.0 из релиза GitHub с проверкой sha256:

```bash
V=v0.34.0; T=appa-aarch64-apple-darwin   # см. таблицу ниже
curl -fsSLO "https://github.com/archestra-ai/OpenAPPA/releases/download/$V/$T.tar.gz"
curl -fsSLO "https://github.com/archestra-ai/OpenAPPA/releases/download/$V/SHA256SUMS"
grep " $T.tar.gz\$" SHA256SUMS | shasum -a 256 -c -   # на Linux: sha256sum -c -
mkdir -p ~/.local/bin && tar xzf "$T.tar.gz" -C ~/.local/bin ./appa && ~/.local/bin/appa --version
```

| Платформа | `T` | sha256 архива |
|---|---|---|
| macOS, Apple Silicon | `appa-aarch64-apple-darwin` | `1e2c916f900d66453660546b7e1c36f19de9f3ef0fa8b6e809863e527c5af686` |
| macOS, Intel | `appa-x86_64-apple-darwin` | `87bd690da28868588f977b63b9fcac1b33dfa97309b82aae74f259e3073af171` |
| Linux, x86_64 | `appa-x86_64-unknown-linux-gnu` | `257755810f3a02934481be9c8dcb74d9e6f309e1d057d884db60cfbefd4cde22` |
| Linux, aarch64 | `appa-aarch64-unknown-linux-gnu` | `93f1243a00ad6e5dec6d670d97384ab580fd7ae5c49030013205b902e0717991` |

Бинарь, на котором сняты `results/` (macOS, Apple Silicon): sha256 `536a3445fdec1105178d7ec36034235e434a4608f6bede5a57688c7ff34a1a93`. На других платформах прогон не делался.

Что печатает `run.sh`:

1. проверку sha256 закреплённого снимка контракта;
2. тесты линтера;
3. линтер на поставляемом контракте, на черновике исправления, на контракте PR #750 и на чужой батарее slack;
4. `appa replay` на трёх моделях (**gap**, **fixed**, **pr750**) и пробах формата;
5. причину каждого отказа (`results/deny-reasons.txt`).

## Исправление

### Вариант «б»: ревью на запись, белый список внутренних папок (`replay/fixed/`)

Мера только средствами формата контракта. Без ревью идёт одно правило: `create_file(parentId:<папка из белого списка>)`. Создание пишет данные траектории, их метку монитор знает. `copy_file` и `update_file` идут на ревью всегда, с любым `parentId`.

Первая версия черновика разрешала без ревью и `copy_file`, и `update_file` в папку из белого списка. Ревью 2026-10-30 нашло, что так проходят обходы: правило `update_file(parentId:…)` совпадало первым и пропускало всё, что едет в том же вызове, — `writersCanShare`, `inheritedPermissionsDisabled: false`, снятие `downloadRestriction`, переименование, перенос в список папки, открытой по ссылке. Правило `copy_file(parentId:…)` пропускало копию файла узкой группы в папку организации. Оба правила убраны; пробы лежат в `replay/fixed/critic-*.appa` и дают `deny`. Линтер теперь ловит этот класс ошибки сам (`access_change_without_review`, `content_not_forwarded`).

**Цена:**

- копия, перенос и переименование даже внутри белого списка уходят на ревью (`replay/fixed/cost-*.appa`);
- `create_file` без `parentId` (корень My Drive) уходит на ревью: отсутствие аргумента селектором не выразить;
- белый список устаревает, если папку расшарят позже: правило верит списку, а не Drive. Та же граница есть у PR #750 («Sharing that changes later… is not seen»).

### Вариант «в»: спросить Drive о читателях цели

Это тоже правка контракта, плюс вспомогательный скрипт. Так сказано и в самом issue: «an annotator or context provider could fetch the same data». Формат даёт два пути:

- **аннотатор** — так сделан PR #750. Правила записей отданы `drive-readers.py`, а он отвечает `requires` и `forwards` по правам цели и источника;
- **аудитория из аргумента** — `requires = { audience = { contains = ["@google-workspace:folder/$parentId"] } }`. Прецедент в поставляемой батарее slack: `contains = ["@slack:channel/$channel_id"]` ([slack/appa.toml, v0.37.0, L153](https://github.com/archestra-ai/OpenAPPA/blob/v0.37.0/marketplace/batteries/slack/appa.toml#L153)). Механизм описан в [contracts.md v0.37.0, «Read a source collection from a tool argument»](https://github.com/archestra-ai/OpenAPPA/blob/v0.37.0/website/content/docs/contracts.md#read-a-source-collection-from-a-tool-argument): «At check time OpenAPPA replaces each `$<argument_name>` with the call's argument value». Источнику аудитории нужен шаблон `folder/<id>`. Этот путь здесь не собирался и не прогонялся.

Вывод агента, не проверен: аудитория из аргумента закрывает только цель. Для источника копии или переноса нужен `forwards`, а у статического `forwards` записи только литеральные (contracts.md: «literal entries only: no `$<argument_name>` placeholders»). Поэтому для `copy_file` и переноса нужен аннотатор, как в PR #750, или ревью, как в варианте «б».

| | Вариант «б» (этот репозиторий) | PR #750 (вариант «в», аннотатор) |
|---|---|---|
| запись, копия, перенос в открытую папку | deny (ревью) | deny (аудитория) |
| копия узкого файла в папку организации | deny (ревью) | deny (`forwards`) |
| `writersCanShare`, `inheritedPermissionsDisabled: false`, `downloadRestriction` | deny (ревью) | allow |
| копия, перенос, переименование внутри организации | ревью | без ревью |
| что нужно в развёртывании | список папок с владельцем | OAuth-скоуп `drive.metadata.readonly`, вызов Drive API на каждую запись |

## Ограничения

- **Копирование и `forwards`.** `copy_file` и перенос (`update_file` с `parentId`) переносят содержимое на стороне Google, мимо траектории: метка траектории ничего не говорит о том, кто читал оригинал. В формате для этого есть `forwards` — «Restrictions carried by content the tool sends beyond its arguments» (contracts.md v0.37.0). Статический `forwards` знает только литералы. По логике самой батареи («A doc read through this battery is `self` data») это `forwards = { audience = ["self"] }`, и тогда копия в папку, которую читает ещё кто-то, отклоняется всегда, даже с ревью. Поэтому вариант «б» отдаёт копию и перенос на ревью, а PR #750 вычисляет `forwards` аннотатором. По коду PR (`content()` в `drive-readers.py`) `internal` получает только файл с грантом на домен Workspace. Файл, открытый группе из одних сотрудников, считается `self`, и его копия в папку организации отклоняется: это консервативная цена PR, а не дыра. Вывод агента по коду, на живом Workspace не проверен.
- Проверка в момент записи. Права, которые меняются после записи, не видны ни варианту «б», ни PR #750.
- Линтер: что расширяет круг читателей, какие аргументы называют цель и какие меняют доступ, перечисляет человек в `checker/inventory.json`. На поставляемом контракте Drive три пробела получаются по построению: инвентарь писался под эту находку. Прогон на slack показывает механику на чужом контракте, но его инвентарь — черновик агента по именам инструментов, схема коннектора Slack не снималась.
- Правило с `annotator` линтер не судит: помечает `annotated_unchecked`, проверка — трассами.
- Replay шёл на `appa` 0.34.0 и только на macOS (Apple Silicon).

## Структура

```
checker/     линтер контракта (contract-as-code), тесты, inventory.json (Drive), inventory-slack.json (черновик)
replay/      модели контракта (gap, fixed, pr750), .appa-трассы, заглушки источника аудитории
             и аннотатора PR #750; разбор в replay/README.md
results/     сырые результаты прогонов, снимки контрактов, снимок PR #750 (upstream-pr750-2a9397b/)
WRITEUP.md   технический разбор: как устроен монитор и почему зазор срабатывает
SOURCES.md   источники с цитатами и закреплёнными версиями
run.sh       воспроизведение одной командой
```
